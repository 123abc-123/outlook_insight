# 认知雷达第一版简要说明

## 1 第一版提供什么

后端只暴露两个业务接口：

| 接口 | 作用 | 主要输出 |
| --- | --- | --- |
| `POST /decompose` | 根据 Topic 和 WebSearch 文献形成面向领导判断的模块结构 | 模块、核心问题、管理价值、证据映射、信息缺口 |
| `POST /update` | 读取 MD 认知报告，生成更新或提交用户确认的候选版本 | 完整候选报告、更新前后文件、逐项修改依据 |

两个接口通过 OpenAPI 自动生成请求和返回结构。启动后可在 `/docs` 查看调试页面，但 `/docs` 不是新增的业务接口。

## 2 拆分接口如何工作

```text
Topic 和文献
  → 逐篇提取证据单元
  → 选择领导需要的分析视角
  → 从证据和管理问题两个方向生成候选模块
  → 合并重复项并审查证据
  → 返回约 4 至 6 个有稳定 ID 的模块
```

模型不会只按文献标题分类。候选模块要说明它支持领导判断什么，例如“技术成熟度与业务适用边界”“投入条件与成本结构”“关键变化与观察信号”。没有证据但会影响判断的问题标为 `gap`，不会补出结论。

拆分接口内部包含三个模型任务：

| 任务名 | 用途 |
| --- | --- |
| `extract_evidence` | 从每份文献提取带原文定位的证据单元 |
| `candidate_modules` | 根据 Topic、领导问题、分析视角和证据生成候选模块 |
| `review_structure` | 合并重复模块，检查边界、管理价值和证据缺口 |

## 3 更新接口如何保证不乱改

更新接口不要求模型重写整篇报告。它把一次更新拆成多个有边界的阶段：

```text
读取最新 MD 文件并验证采纳记录和版本
  → 只读取被采纳的回答片段
  → 用本轮文献和相关历史文献核实认知增量
  → 召回相关章节和正文块
  → 生成指向具体正文块的修改操作
  → 检查受影响的摘要和建议
  → 程序校验并生成完整候选报告
  → 普通正文自动提交；核心内容或结构变化等待用户确认
```

更新由三层约束共同控制：

1. **采纳范围**决定本轮可以处理哪些回答内容。未采纳片段不会进入模型上下文。
2. **证据范围**决定什么内容可以写入。引文必须是输入文献片段的逐字子串；新增数字和单位必须能在引用中找到。
3. **对象范围**决定哪里可以修改。模型只能修改程序召回的正文块；只有请求明确设置 `allow_structure_change=true` 时才能新增或重命名章节。删除、移动章节及重写全文始终禁止。

每个修改操作必须携带目标块 ID、旧文本哈希、本轮增量 ID、证据、修改理由、位置理由和对领导判断的影响。程序会拒绝伪造引用、修改无关章节、使用过期版本或重复提交。

### 3.1 文件版本

接口中的 `report_path` 是 `[reports] root_dir` 下的相对路径。例如 `report_path = "ai-agent.md"` 实际读取 `reports/ai-agent.md`。接口不接受目录外路径。

第一次更新时，原始文件会复制为：

```text
data/report_versions/<report_id>/v000001.md
```

更新成功后新建：

```text
data/report_versions/<report_id>/v000002.md
data/report_versions/<report_id>/v000002_changes.md
```

以后每次调用都自动读取最新版本并新建 v3、v4。原始文件及所有历史版本均不覆盖。接口同时返回 `before_report_path`、`after_report_path` 和 `change_log_path`。SQLite 只保存版本号、文件哈希和幂等记录，报告正文始终存放在 MD 文件中。

`report_path` 在第一次调用后作为这份报告的登记标识。后续更新以历史目录中的最新版本为准，不会重新读取尚未变化的原始文件；这样可以保证每轮都接着上一次结果修改。如果需要人工修改当前报告，应把人工修改登记成一个新版本，不能直接改历史文件。历史文件的哈希发生变化时，接口会拒绝继续更新。

请求中的 `expected_version` 用于防止用户基于旧报告提交修改。如果当前已是 v3，而请求声明基于 v2，接口返回 `version_conflict`，不会覆盖 v3。

更新请求的核心结构如下，文献元信息可继续放在 `metadata` 中：

```json
{
  "action": "prepare",
  "request_id": "update-20260905-001",
  "report_path": "ai-agent.md",
  "expected_version": 3,
  "adoption": {
    "adoption_id": "adoption-001",
    "turn_id": "turn-18",
    "answer_revision": "answer-v1",
    "accepted_segment_ids": ["answer-part-2"]
  },
  "current_turn": {
    "turn_id": "turn-18",
    "question": "现在是否适合扩大试点",
    "answer_revision": "answer-v1",
    "answer_segments": [
      {"segment_id": "answer-part-2", "text": "被用户采纳的回答内容"}
    ],
    "documents": [
      {
        "document_id": "internal-35",
        "title": "试点运行记录",
        "source_type": "internal",
        "segments": [
          {"segment_id": "p8", "text": "用于支持本轮回答的原文片段"}
        ],
        "metadata": {"published_at": "2026-09-01"}
      }
    ]
  },
  "historical_documents": [
    {
      "document_id": "internal-12",
      "title": "上一阶段试点记录",
      "source_type": "internal",
      "segments": [
        {"segment_id": "p3", "text": "旧观点原来依赖的历史证据原文"}
      ],
      "metadata": {"published_at": "2026-06-01"}
    }
  ],
  "confirmation_policy": "auto_routine",
  "allow_structure_change": false,
  "previous_turn": {
    "question": "先从哪个场景开始",
    "answer": "上一轮回答，只用于解释指代和上下文"
  }
}
```

`confirmation_policy="auto_routine"` 表示普通正文修改可自动提交；修改管理摘要、核心结论、建议，或者执行章节新增和改名时，接口返回 `preview_ready`、`preview_id` 和完整 `candidate_report`，不创建新版本。若要求所有修改都先确认，可设置 `confirmation_policy="always"`。

用户检查完整候选报告后，仍调用同一个接口提交：

```json
{
  "action": "commit",
  "request_id": "commit-20260905-001",
  "report_path": "ai-agent.md",
  "preview_id": "p_xxxxxxxxxxxxxxxxxxxxxxxx",
  "confirmed": true
}
```

提交阶段不调用模型，保存内容必须与 `candidate_report` 逐字一致。预览以后如果报告已经产生新版本，提交返回 `version_conflict`，要求基于最新报告重新生成预览。

### 3.2 完整报告与审计记录

领导的主要阅读对象是更新后的完整报告。系统必须先保证摘要、正文、核心判断和建议一致，并在需要确认时返回完整 `candidate_report`，不能要求领导依赖变更说明理解当前结论。

`vXXXXXX_changes.md` 主要用于报告负责人复核和研发审计，按修改逐项展示：

- 修改发生在哪个章节，以及为什么应该放在这里；
- 修改前和修改后的完整文字；
- 对应的用户采纳片段；
- 支持该修改的文献 ID、片段 ID 和原文；
- 这项修改对领导判断有什么影响；
- 独立审查为什么认为证据足够、位置合适，以及仍有哪些限制。
- 程序已经通过了哪些确定性检查，包括采纳范围、引文、数字、目标哈希和未修改内容保护。

程序先核对引用确实存在、新增数字能在证据中找到、目标块没有被其他请求修改；最终审查再判断证据是否真的支持新表述、适用范围是否被扩大、限定是否丢失。任一检查失败都不生成新报告版本。

更新接口内部包含五个模型任务：

| 任务名 | 用途 |
| --- | --- |
| `resolve_scope` | 用当前问答和上一轮语境解析本轮讨论范围 |
| `extract_deltas` | 从采纳片段提取并核实认知增量 |
| `plan_update` | 比较认知增量与旧报告正文，提出局部修改操作及位置理由 |
| `review_dependencies` | 判断相关摘要和建议是否需要同步变化 |
| `review_update` | 逐项审查证据、修改位置、适用范围及前后矛盾 |

如果证据不足、存在关键歧义或审查不通过，接口返回原因并保留旧报告。相同 `request_id` 重试返回相同结果；同一报告发生并发更新时，只有基于当前版本的请求能够提交。

## 4 大模型配置

主配置文件是 [`config/radar.toml`](../config/radar.toml)。它把模型连接与任务参数分开：

```toml
[app]
model_mode = "live"
database_path = "data/radar.sqlite3"

[reports]
root_dir = "reports"
history_dir = "data/report_versions"

[llm_profiles.default]
url = "http://公司内网模型地址/v1/chat/completions"
model = "公司提供的模型名"
api_key_env = "RADAR_LLM_API_KEY"
timeout_seconds = 90
temperature = 0.0
max_tokens = 6000

[tasks.plan_update]
profile = "default"
temperature = 0.0
max_tokens = 7000
```

如果某个任务要使用更强的模型，可以增加一个 `llm_profiles.large`，再把 `tasks.plan_update.profile` 或 `tasks.review_update.profile` 改成 `large`。每个任务都可覆盖 `temperature`、`max_tokens`、`top_p`、`timeout_seconds` 和 `max_context_chars`。

Key 有两种配置方法：

- 推荐使用 `api_key_env`，部署时设置对应环境变量。
- 内网环境也可在本地配置中填写 `api_key = "..."`。建议复制成 `config/radar.local.toml`，该文件已被 Git 忽略。

启动时通过 `RADAR_CONFIG` 选择配置文件：

```powershell
$env:RADAR_CONFIG = "config/radar.local.toml"
$env:RADAR_LLM_API_KEY = "公司提供的 Key"
.venv\Scripts\python.exe -m uvicorn radar.main:app --host 0.0.0.0 --port 8000
```

当前 HTTP 客户端适配 OpenAI Chat Completions 兼容协议。如果公司的协议不同，只需要替换 `radar/model.py` 中的模型适配层，两个业务接口和更新校验逻辑不需要改。

## 5 当前代码位置

| 路径 | 内容 |
| --- | --- |
| `radar/api.py` | 两个 HTTP 接口 |
| `radar/decompose.py` | 拆分流程 |
| `radar/markdown_update.py` | MD 报告更新编排与合理性审查 |
| `radar/markdown.py` | Markdown 分块、召回、局部修改和校验 |
| `radar/markdown_store.py` | 历史文件、变更说明和版本记录 |
| `radar/model.py` | 内网大模型 HTTP 适配 |
| `radar/config.py` | TOML 配置读取和合法性检查 |
| `radar/store.py` | SQLite 连接、幂等与事务基础能力 |
| `tests/test_radar.py` | 接口和边界测试 |

第一版假定上游已提供文献元信息和可定位的正文片段。模型调用返回结构化 JSON；文献量超过单次上下文上限时明确报错，不会静默截断材料。
