# 认知雷达报告更新实现方案

版本：实现稿 v1.1

适用环节：用户采纳一轮回答后，将有效认知增量写入当前报告

读者：产品与研发人员

> 当前实现说明：认知报告正文存储在 Markdown 文件中。`/update` 的 `prepare` 动作读取 `report_path` 的最新版本，将正文映射成可校验的内容块，并分别接收本轮文献与 `historical_documents`。普通正文可以按策略自动提交；管理摘要、核心结论、建议以及章节结构变化返回完整候选报告等待确认。`commit` 动作只提交该候选原文，不再次调用模型。所有正式版本和变更说明永久保留。

## 1 设计结论

更新接口应实现“有证据的观点变更”，以当前报告为基线，先找出本轮真正改变的认识，再生成有明确目标的修改操作，由程序校验和应用。

不建议把本轮问题、回答、全部文献、上一轮问答和旧报告直接拼成一个长提示词，让模型返回整篇新报告。这样难以约束修改范围，也难以解释哪些改动来自证据、哪些只是模型换了一种说法。

推荐流程如下：

```text
锁定被采纳内容与报告基线
    ↓
提取本轮认知增量并核对证据
    ↓
检索相关旧观点及其历史证据
    ↓
判断新旧关系并生成局部修改方案
    ↓
检查受影响的摘要和建议
    ↓
校验修改范围  引用  数字  语义  版本
    ↓
生成完整候选报告并判断是否需要确认
    ↓
自动提交普通更新，或在用户确认后原子写入候选版本
```

领导的主要阅读对象是完整报告，因此每次更新都要保证摘要、正文、核心判断和建议一致。变更说明作为报告负责人和研发人员的审计记录，支持定位问题和追溯来源。

## 2 每类输入应怎样使用

文献元信息复用现有能力。本功能主要增加输入之间的职责区分与关联，不另建元信息采集流程。

| 输入 | 在更新中的作用 | 不应承担的作用 |
| --- | --- | --- |
| 当前报告及版本 | 提供旧观点、模块边界、摘要、建议和历史证据关系 | 不能默认旧报告每个事实都正确 |
| 本轮问题 | 识别用户关注对象、范围和条件 | 问题中的猜测不能直接当事实 |
| 本轮被采纳回答或片段 | 确定拟更新的内容与意图 | 用户采纳不等于其中所有事实已验证 |
| 本轮文献及数据 | 支持、限制或反驳拟更新观点 | 不把检索到但与采纳内容无关的材料全部写入 |
| 上一轮问题和回答 | 解析“这个方案”“继续推广”等指代，补足对话约束 | 不自动重复写入，也不自动当作证据 |
| 相关历史证据 | 核实旧结论的基础，判断是否真正被新材料改变 | 不能只看本轮结果就断定旧结论失效 |
| 明确的用户偏好 | 记录“优先考虑成本”等决策约束 | 不伪装成客观事实或文献结论 |

建议用独立字段传入这些内容，不把它们混成一个无法分辨来源的字符串。每个模型调用只读取本阶段需要的分区，并保留引用 ID。

上一轮对话默认仅用于语境解释。如果“这个方案”仍无法解析，可按指代回查更早的相关轮次；不能只因位置最近就认定指代对象，也不应将全部聊天历史无差别加入上下文。

### 2.1 多来源文献如何取舍

更新不设置“内部来源永远优先”或“最新来源自动覆盖”的统一排名。每个待写入主张分别检查五项：内容是否直接支持、是否适用于长鑫、方法和口径是否透明、时效是否仍有效、来源是否独立。相关性是硬门槛，其他因素用于决定材料能支持多强的表述。

| 待核实内容 | 优先材料 | 使用边界 |
| --- | --- | --- |
| 公司良率、成本、产能、交付和客户状态 | 有权限的内部原始数据、正式记录、可复核计算 | 外部报道不能替代内部经营事实 |
| 市场规模、价格、库存和竞争动作 | 监管披露、公司公告、一手市场数据 | 区分事实、机构估计和预测 |
| 技术成熟度与量产能力 | 标准、论文、专利、测试数据、客户认证和量产记录 | 研发样品不能直接等同稳定量产 |
| 政策与合规 | 法律法规、主管机构文件和正式解释 | 媒体解读只作为线索或观点 |
| 战略判断与预测 | 多个独立来源及明确推导 | 必须保留假设、适用范围和不确定性 |

同一底稿的转载按一个 `family_id` 处理，不能因转载数量多而提高权重。来源冲突时先检查时间、对象、场景、样本和统计口径；不能消解的冲突在报告中保留分歧和待验证条件。

## 3 先让报告具备可定位的观点结构

### 3.1 推荐的最小存储结构

展示模板尚未确定，不影响先建立稳定的内容结构。建议以“报告—模块—观点”为主体，并让摘要和建议引用它们依赖的观点。

```ts
type Claim = {
  claim_id: string;
  claim_revision: number;
  module_id: string;
  kind: "fact" | "assessment" | "recommendation" | "user_constraint";
  text: string;
  applicability: string[];       // 对象、时间、场景及条件
  evidence_links: {
    ref: EvidenceRef;
    relation: "supports" | "contradicts" | "qualifies";
  }[];
  depends_on_claim_ids: string[];
  status: "active" | "disputed" | "superseded";
};

type ReportSnapshot = {
  report_id: string;
  topic: string;
  version: number;
  modules: Module[];
  claims: Claim[];
  summary_items: DerivedItem[];
  recommendation_items: DerivedItem[];
};
```

`DerivedItem` 至少包含稳定 ID、文本、修订号及依赖的观点 ID。新版本中被替代的观点应退出当前有效内容，旧文本在历史版本中保留；不能悄悄删除历史，也不能让相反版本同时作为当前结论展示。

事实需要对应直接证据或可复核计算；判断需要注明依据与限定条件；建议需要关联支持它的判断与约束。用户偏好以“用户要求”记录，不能冒充证据支持的事实。

### 3.2 如果现在只有 Markdown 报告

第一版可保留 Markdown 展示，但在首次接入时按标题和段落建立结构索引，保存稳定模块 ID、段落 ID、文本哈希及可定位的观点。系统应保存 ID 与内容的映射，不能每次根据段落序号重建 ID。

对同一段落包含多个判断的情况，先拆成内部观点，再在渲染时合并。暂时无法拆分时使用“段落 ID + 旧文本哈希”替换整段，并检查该段中未获授权的观点没有变化。不要对整篇报告做任意字符串替换。

对旧报告中无法追溯来源的观点，标记历史证据缺失。可以基于新证据添加限定或待验证说明，但不能因为本轮没有检索到旧来源就自动判定旧结论错误。

## 4 更新接口设计

### 4.1 请求

```ts
type UpdateReportRequest = {
  report_id: string;
  base_version: number;
  request_id: string;               // 同一逻辑更新的幂等键
  adoption: {
    adoption_id: string;
    turn_id: string;
    answer_revision: string;
    accepted_segment_ids: string[];
  };
  current_turn: {
    question: string;
    answer: string;
    documents: DocumentRef[];
  };
  previous_turn?: {
    turn_id: string;
    question: string;
    answer: string;
  };
};
```

服务端通过 `report_id` 读取指定版本的报告及相关历史证据。若现有接口只能传完整报告，也应核对其版本与内容哈希，不能将客户端任意传来的文本直接作为可信基线。

服务端验证采纳记录确实对应指定轮次、回答修订和片段；不能由模型猜测用户采纳了什么。若产品只有“整条采纳”，服务端将全部回答片段展开为采纳范围。没有采纳记录时，这个接口不提交报告修改。

建议在创建回答时就保存片段 ID 和引用关系。没有片段 ID 的存量回答，可一次性分段后固定映射。回答发生修改后必须使用新的回答修订号，避免用户采纳的是 A 版，更新时却读取 B 版。

### 4.2 返回

```ts
type UpdateReportResult = {
  status: "updated" | "no_change" | "needs_clarification"
        | "evidence_insufficient" | "version_conflict" | "failed";
  report_id: string;
  base_version: number;
  new_version?: number;
  changes: ChangeSummary[];
  unresolved_items: UnresolvedItem[];
  request_id: string;
};
```

`no_change` 表示完成比对但没有需要修改的内容，也记录本次处理结果。新增了有效引用，即使正文未改变，仍属于 `updated`，可在变更说明中标为“证据补充”。`needs_clarification` 用于影响结论的指代或采纳范围无法确定；`evidence_insufficient` 用于无法形成可提交的证据支持更新。

接口可同步或异步执行。耗时较长时可先返回任务 ID，再读取上述结果；这属于执行包装，不改变更新规则。

## 5 核心算法

### 5.1 阶段一 解释本轮意图并固定范围

输入只包含 Topic、当前问题、被采纳回答和必要的历史对话。输出包括讨论对象、本轮关心的问题、明确的约束、指代解析结果及采纳边界。

例如上一轮讨论“先做内部知识问答试点”，本轮问题是“那什么时候可以扩大”，历史问答用于说明“扩大”的对象是该试点，不意味着上一轮全部回答都要再次更新到报告。

用户问题中的反问、假设和试探必须保留语气。例如“如果成本降一半，是不是可以推广”属于假设分析，不能写成成本已经下降。

### 5.2 阶段二 提取并核实认知增量

把采纳内容拆成可以独立核实的候选观点。每项关联具体回答片段、相关证据、适用条件，并区分事实、判断、建议和用户约束。

```ts
type CandidateDelta = {
  delta_id: string;
  accepted_segment_ids: string[];
  proposition: string;
  kind: Claim["kind"];
  applicability: string[];
  supporting_refs: EvidenceRef[];
  contradicting_refs: EvidenceRef[];
  reasoning?: string;             // 简短、可审查的依据说明
  support_status: "supported" | "partial" | "unsupported";
};
```

核实过程先使用回答已有引用，再在本轮检索材料中查找相关支持、限定和反证。对准备修改的观点，应查看本轮相关材料中的反向证据，不能只挑支持答案的片段。

如果本轮材料不足，可从已有知识库检索相关历史来源；需要新的外部材料时向上游检索服务发请求。离线环境无法补充时保留未解决项，不编造支持。

处理规则：

- 证据完整支持时，进入新旧观点比对。
- 证据只支持更窄结论时，只能保留更窄且与采纳内容相容的表述，并说明被排除的泛化部分。
- 对只有假设的内容，若值得保留，写成假设或待验证问题。
- 采纳回答包含明显事实错误时，不把错误写入。若纠正将改变被采纳答案的实质含义，返回待处理事项；用户对原答案的采纳不能被解释成对相反新答案的采纳。
- 与采纳内容无关的新材料，不产生独立更新。它只有在限制或反驳当前候选时才进入本次核实。

不要用一个模型自报的置信分数替代证据核对。来源可信、内容支持、场景适用和时效有效是不同检查。

### 5.3 阶段三 找到相关旧观点

先根据模块核心问题定位候选模块，再用关键词与语义检索寻找旧观点，最后读取候选观点的完整文字、适用条件和历史证据。相似度用于召回，不能直接决定“新观点替换旧观点”。

比较至少检查：是否同一对象、同一指标、同一时间范围、同一应用场景及同一统计口径。两句话名称相似但范围不同，不构成直接冲突。

例如“试点咨询的平均处理时间下降”和“公司客服总成本下降”是不同主张；后者还需要人工复核、运行成本、咨询量等证据，不能用前者直接替换。

### 5.4 阶段四 判断关系并提出操作

| 新旧关系 | 处理方式 | 需要提供的理由 |
| --- | --- | --- |
| 重复且没有新增支持 | 不修改 | 已有观点 ID 与等价依据 |
| 结论相同但有新的有效证据 | 仅增加证据链接 | 新来源为何独立、适用或更直接 |
| 增加条件或适用范围 | 修改具体条件，保留其余判断 | 新条件对应的证据 |
| 新增独立认识 | 在现有模块新增观点 | 为何不是已有内容的重复 |
| 同口径事实被更正 | 替代旧事实，保留历史 | 更正依据及新旧口径一致性 |
| 不同时间的有效数据 | 保留时间序列，更新当前时点判断 | 新数据适用时间及可比性 |
| 同范围证据相互矛盾 | 标为存在分歧或缩小结论 | 双方证据与尚未解决的问题 |
| 外部结论不适用本公司 | 保留外部观察，限定内部适用性 | 公司具体条件的支持材料 |
| 新证据不足以支持原建议 | 调整建议条件或转为待验证 | 哪条前提变化导致建议变化 |

相互冲突时，先排除时间、口径、样本和场景差异，再比较证据的直接性、方法透明度、有效时间和来源独立性。不能按来源篇数投票，也不能简单执行“最新文献覆盖旧文献”。

对于无法判断胜负的同范围冲突，报告应写明分歧及待验证事项。只有出现可核查的更正、失效依据或充分的反证时，才把旧观点标为被替代。

### 5.5 阶段五 检查摘要与建议

观点改变后，查询依赖它的摘要条目、建议和其他派生判断，形成受影响集合。逐项检查是否需要同步修改，并让每项修改指向触发它的观点变化。

例如正文从“试点可以推广”变成“试点效果受限，尚需验证成本”，摘要就不能继续写“具备全面推广条件”。但正文新增一个辅助案例，不应引发摘要和全篇措辞重写。

对存量报告没有依赖关系的情况，检索全篇可能引用旧数字、旧对象或旧建议的位置，生成待核查位置；最终再做一次全篇矛盾检查。该检查负责发现问题，不获得任意改写全文的权限。

在当前报告中区分“方案建议”与“已批准行动”。认知报告更新可以调整建议，但不能把用户采纳回答写成公司已经批准预算、落实责任人或执行了项目。

## 6 用修改计划约束模型输出

### 6.1 每个修改必须同时有目标和理由

```ts
type PatchOperation = {
  operation_id: string;             // 本次计划内唯一，服务端检查并保存
  op: "add_claim" | "revise_claim" | "add_evidence"
    | "mark_disputed" | "supersede_claim"
    | "revise_derived_item" | "add_module";
  target_id?: string;
  target_module_id: string;
  expected_revision?: number;
  expected_text_hash?: string;
  after: object;
  delta_ids: string[];
  caused_by_operation_ids: string[];
  evidence_refs: EvidenceRef[];
  reason: string;
};
```

实际实现应按 `op` 定义互斥的具体 Schema，限制 `after` 可修改字段。上面使用 `object` 只是展示公共结构，生产接口不能允许模型写入任意字段。

例如 `revise_claim` 可以修改观点文本、条件和证据关系；不能修改报告 ID、用户身份、模块所有权或已有历史版本。`add_evidence` 只增加去重后的引用，不重写文本。新增 ID 由程序生成。

原始观点修改必须关联采纳片段对应的 `delta_ids`；摘要或建议的联动修改还必须关联触发它的操作 ID。每项变更都能回答：改哪里、原来是什么、改成什么、为何需要改、依据在哪里。

### 6.2 限制模块变更

默认在现有模块中更新，不因一轮问答重新拆分全篇。新增模块需要同时满足：与 Topic 直接相关、具有独立的管理问题、现有模块边界无法容纳、在本轮采纳范围内有实质内容支持。

当前版本支持符合条件的新增章节和章节改名，并强制进入完整报告确认流程。暂不自动执行模块合并、删除、移动和全篇重排。跨多个模块的新观点优先放入一个主模块并建立引用，避免同一判断复制多份后分别演化。

### 6.3 修改范围检查

服务端由“被采纳的候选观点 → 相关旧观点 → 必要依赖项”计算允许修改的集合。模型输出中的目标必须落在这个集合中。需要扩展范围时，必须先返回关联依据并通过范围检查，不能直接提交越界修改。

对未触及对象比较内容哈希，确保保持不变。正文渲染过程中可以发生分页或自动编号变化，这与观点变化分开记录；展示层调整不得改变未获授权的结论。

### 6.4 修改计划生成的任务约束示例

```text
你负责提出报告局部修改计划，不直接输出整篇新报告。

输入分区：
A 已核实的本轮增量及其被采纳片段 ID
B 相关旧观点及模块边界
C 新旧证据的原文片段及适用条件
D 允许修改的目标集合

逐项判断增量与旧观点的关系：重复、补充、限定、修正、冲突或新增。
仅使用输入中已有的观点 ID、增量 ID 和证据 ID。
每个操作给出修改目标、旧版本条件、新内容、引用和简短修改理由。
没有增量时输出空操作数组，不通过换一种说法制造更新。
不改变证据未涉及的条件，不扩大被采纳内容的含义。
缺少支持或无法解决冲突时输出未解决项，不自行补足事实。
摘要和建议的联动修改必须关联触发它的具体操作。
只输出约定结构中的 operations 和 unresolved_items。
```

最终审查任务使用不同的任务说明：逐项判断证据能否支持修改、目标是否越界、限定是否丢失；返回操作 ID、错误类型和需要修正的内容。提示词负责语义约束，目标集合与字段权限仍由程序强制执行。

## 7 写入前校验与事务处理

### 7.1 程序负责的确定性校验

1. 采纳记录、回答修订、片段 ID 与请求一致，访问范围与报告一致。
2. 修改操作符合 Schema，目标存在且修订号匹配，新增 ID 无冲突。
3. 引用存在，指向可解析的文献片段或数据记录；读取缺失时不视为验证通过。
4. 事实中的数字、单位、日期及比较基准与来源或已记录的计算过程一致；派生比例由程序复算。
5. 修改对象属于允许集合，未触及对象哈希一致。
6. 依赖引用没有悬空，受影响的摘要与建议已检查。

自然语言条件和跨材料推导不能完全靠规则核对。确定性校验通过之后，仍需进行语义审查。

### 7.2 独立语义审查

单独调用审查任务，读取新旧文本、引用原文、采纳范围和修改理由，检查：证据是否蕴含新表述、是否扩大了适用范围、是否把相关性写成因果、是否遗漏反证、是否把建议写成已执行事实，以及摘要与正文是否一致。

审查输出 `pass / revise / reject` 和逐项错误，不输出一篇自由重写的新报告。生成和审查可以使用同一个模型的不同调用，第一版不要求多智能体；但需要认识到同一模型可能重复犯错，最终仍用真实样本和人工复核评估效果。

错误允许一次受约束的修复，再完整复验。仍不通过就返回失败或证据不足，保留当前报告，不能为了让接口“成功”而跳过检查。

### 7.3 预览、确认、提交与幂等

实现包含两个核心函数：

- `prepare_markdown_report_update` 读取最新版本并生成候选报告。普通正文按配置自动提交；修改管理摘要、核心结论、建议或章节结构时返回 `preview_ready`，并明确 `confirmation_required=true`。
- `commit_markdown_report_update` 接收 `preview_id` 和用户确认，只写入预览时保存的候选原文。该函数不得调用模型，也不得重新生成或修饰报告。

如果预览生成以后报告版本发生变化，旧预览不得提交，必须基于最新版本重新比较。这样用户确认的内容与最终正式版本保持逐字一致。

在事务中按 `base_version` 比较并更新报告版本，同时保存新内容、证据关系、修改记录和请求结果。任一保存失败，整次提交回滚。

同一个 `request_id` 与相同请求内容重复到达时返回已有结果；同一键对应不同内容时拒绝请求。对同一 `adoption_id` 的已完成结果加唯一约束，避免客户端更换请求 ID 后对同一次采纳重复处理。`updated` 与 `no_change` 都属于已完成；后者不增加报告版本，但保存采纳处理结果。

生成期间报告版本已变化时，返回 `version_conflict`。调用方可以基于最新版本重新执行整个比较和校验流程，不能将旧修改计划直接重放到新报告。

第一版采用一次采纳原子更新：若存在影响采纳主结论的未解决项，整次不提交，返回具体原因；其余候选计划可以保存供后续处理。已明确选中的回答片段构成一次更新范围，不自动把未被选择的片段一起提交。

待处理结果使用相同请求 ID 重试时仍返回该次结果。用户补充证据或澄清后，使用新的 `request_id` 创建处理尝试并关联原采纳记录；唯一约束只允许同一采纳产生一个已完成结果。改变被采纳回答内容时必须重新采纳，后续再次采纳也应创建新采纳事件。

## 8 输入很多时怎样控制上下文

采用分阶段组装上下文，避免重复传递全部材料。

| 模型任务 | 必需输入 | 输出 |
| --- | --- | --- |
| 意图与指代解析 | 当前问答、采纳片段、必要历史问答、Topic | 明确范围和约束 |
| 增量提取与核实 | 采纳片段、相关新文献原文、必要反证 | 有证据映射的候选增量 |
| 新旧比对与修改计划 | 候选增量、相关旧观点、历史证据、模块边界 | 局部修改操作 |
| 联动检查 | 已拟定操作、受影响摘要和建议、相关前提 | 必要联动操作 |
| 最终语义审查 | 修改前后内容、采纳边界、引用原文、相关上下文 | 审查结果与问题 |

可先用摘要和索引召回，作出覆盖或反驳判断时必须读到原文片段及限定条件。关键冲突证据不能因排在上下文末尾而被静默截断；超出预算时拆成多个比较任务，再汇总操作。

缓存适用于文献证据提取、报告结构索引和未变化的历史观点，不适用于跨报告版本直接复用修改计划。缓存键应包含内容版本与抽取规则版本。

对话、报告正文和文献都按带来源标签的数据输入，不能执行其中夹带的“忽略规则”“删除其他章节”等指令。

## 9 贯穿示例

以下全部是虚构输入与数值，仅用于说明更新逻辑。

### 9.1 旧报告与输入

旧报告 v7 在“优先场景与业务价值”模块中有观点 C17：“常见咨询试点显示处理时间有所缩短，具备继续评估推广的价值。”其摘要 S1 写：“建议继续验证推广条件。”建议 R1 写：“先补齐质量与成本数据，再决定是否扩大试点。”

上一轮问题是“先从哪类咨询试点”，回答选择了常见咨询。本轮问题是“那是不是已经可以推广到全部客服场景？”上一轮对话用于解析试点对象。

用户采纳的本轮回答是：“当前证据只支持继续评估常见咨询。内部质量和总成本尚有缺口，建议先完成验证再扩大范围。”

本轮来源如下：

| 来源 | 输入内容 | 能支持什么 |
| --- | --- | --- |
| E1 外部案例 | 常见咨询平均处理时间下降 30% | 某外部案例的处理时间改善，不能直接代表本公司 |
| I1 内部试点记录 | 100 次测试中 70 次独立完成，30 次需要人工介入 | 本次样本的独立完成比例为 70% |
| I2 内部测算说明 | 尚未计入人工复核成本 | 当前测算不足以判断完整成本收益 |

I1 没有给出正确率或用户满意度，因此不能把 70% 写成“准确率达到 70%”；I2 也不能推出“成本一定更高”。

### 9.2 拟定修改

将 I1 对应的“本次测试独立完成比例为 70%”作为新事实加入能力边界相关模块，保留样本和人工介入说明。将 I2 对应的成本缺口写入投入条件模块。

C17 的“继续评估推广的价值”与本轮并不矛盾，可补充限定：“当前证据仅覆盖常见咨询，尚不足以推断全部客服场景的推广效果。”如果旧文本本来已经包含同样限定，则不改文本，仅补充有效新证据。

S1 的总体判断仍然成立，不需要换一种说法重新生成；R1 可补充“人工复核成本”这一明确的验证项。其他模块保持不变。

对领导返回的变更说明可以是：“补充了内部试点数据，并明确当前结论只适用于常见咨询；推广前需补齐人工复核成本等验证信息。继续验证的总体建议不变。”

### 9.3 如果新证据确实推翻旧判断

假设另一份旧报告明确写着“已经具备全场景推广条件”，且历史证据只覆盖常见咨询。本轮证据揭示了该泛化缺口，那么修改 C17 后，还必须同步修正依赖它的摘要和推广建议，并记录“原判断超出了证据适用范围”的原因。

如果采纳的回答反而声称“70% 独立完成证明全面推广已成熟”，新材料无法支持该推导。接口应返回待处理原因，保留旧报告，不能因用户点击采纳而升级为确定性推广建议。

## 10 服务端伪代码

```python
def update_report(req):
    existing = lookup_attempt(req.request_id)
    if existing:
        assert_same_request(existing, req)
        return existing.result

    adoption = validate_adoption(req.adoption, req.current_turn)
    completed = lookup_completed_adoption(adoption.id)
    if completed:
        return completed.result

    base = load_report(req.report_id, req.base_version)
    scope = resolve_scope(req, adoption, base.topic)
    if scope.has_material_ambiguity:
        return persist_noncommit_result(req, "needs_clarification")

    deltas = extract_and_ground_deltas(scope, req.current_turn.documents)
    old_context = retrieve_claims_and_evidence(base, deltas)
    plan = compare_and_plan(deltas, old_context, base.modules)
    plan = check_dependent_summaries_and_recommendations(base, plan)

    if plan.has_material_unresolved_items:
        return persist_noncommit_result(req, "evidence_insufficient", plan)

    if not plan.operations:
        return complete_adoption_without_revision(req, adoption, base, plan)

    allowed_targets = derive_allowed_targets(base, deltas, old_context)
    candidate = apply_to_copy(base, plan, allowed_targets)
    validate_schema_refs_numbers_scope(base, candidate, plan)
    review = review_semantics(base, candidate, plan, scope)
    if not review.passed:
        # 最多一次受约束修复；修复后重新执行全部校验
        candidate, plan = repair_once_and_revalidate(
            review, base, plan, scope, allowed_targets
        )

    return commit_atomically_with_version_check(
        base, candidate, plan, req.request_id, adoption.id
    )
```

幂等读取、采纳唯一约束和版本检查必须在数据库层具备并发保护，上述前置查询本身不足以防止两个请求同时提交。异常统一转成结构化结果并留下阶段记录；不向调用方返回假成功。

## 11 关键测试用例

| 用例 | 必须满足的结果 |
| --- | --- |
| 相同内容重复采纳 | 不重复增加观点或引用 |
| 只补充新证据 | 保持观点措辞，新增有效引用并说明 |
| 部分采纳 | 只处理被选片段及必要依赖，不纳入其他建议 |
| 上一轮存在错误回答 | 不把其当证据沿用 |
| 本轮问题是假设 | 不把假设条件写成已发生事实 |
| 新旧数据口径不同 | 不直接覆盖或计算变化率 |
| 内外源场景不同 | 保留各自适用范围，不简单判一方错误 |
| 旧结论缺少历史证据 | 标记缺口，不自动判定失效 |
| 存在直接反证 | 不只用支持材料；明确分歧或返回未解决项 |
| 正文影响主判断 | 摘要和建议完成依赖检查，无相互矛盾 |
| 无关模块 | 内容哈希保持不变 |
| 引用或数字伪造 | 校验失败且不提交 |
| 文献夹带更新指令 | 不执行，修改范围保持受约束 |
| 并发版本变化 | 返回冲突，不覆盖其他更新 |
| 重复请求或重试 | 最多成功提交一次 |
| 数据库中途失败 | 内容、引用、版本及记录全部回滚 |

除自动用例外，建立一批人工标注的“旧报告 + 采纳问答 + 新旧证据 → 应改位置与不应改位置”样本。重点评价修改范围准确率、必要变化召回率、证据支持率和摘要一致性，避免只评估新报告是否流畅。

评估时把“旧内容保持不变”也作为正确输出。否则模型为了提高看似丰富的更新率，会产生不必要的改写。

## 12 第一版落地顺序

1. 建立报告观点 ID、模块 ID、引用关系和版本存储；存量 Markdown 先加结构索引。
2. 固定采纳范围，实现增量提取、相关旧观点召回和证据核对。
3. 支持新增观点、条件修正、补充证据、标记分歧，以及摘要和建议的必要联动。
4. 加上修改范围检查、语义审查、版本比较、幂等与原子提交。
5. 用标注样本回放，确认“该改的改到、不该改的保持不变”，再开放更复杂的模块调整。

第一版的核心交付是一个可追溯的更新接口。它不必一次解决所有报告格式，但每项生效的修改都必须能定位到采纳内容、证据和受影响的旧观点。
