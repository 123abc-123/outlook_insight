# 关键词与子问题生成方案

## 1 先区分两种关键词

当前最容易出现的问题，是把“报告模块名称”和“搜索关键词”当成同一个东西。两者目标不同，应分别生成和评估。

| 产物 | 使用者 | 目标 | 示例 |
| --- | --- | --- | --- |
| 模块短标题 | 领导、报告目录、前端导航 | 一眼看出需要判断什么 | 模型架构、落地场景、存储需求 |
| Web Search 查询 | 检索服务 | 找到能支持、限定或反驳判断的材料 | 深度学习训练 内存带宽 DRAM 需求 2026 一手数据 |

模块标题需要短、稳定、同层级；查询词需要具体、可扩展，并主动覆盖反向观点。不要用同一 Prompt 一次性同时生成两者。

## 2 什么样的模块标题更容易让领导满意

领导通常关心的不是“材料讲了什么”，而是“这件事影响哪个判断”。一个合格模块至少满足五项：

1. **直接相关**：与 Topic 和本次领导问题直接相关。
2. **有决策用途**：可能影响优先级、资源、选项、风险或行动时点。
3. **边界清楚**：与其他模块回答不同问题，不能同义重复。
4. **证据可承载**：当前材料足以讨论，或明确标记为关键证据缺口。
5. **名称可扫读**：2—6 个字，使用具体名词短语，避免“背景、现状、趋势、挑战”等空泛词。

短标题只是显示层。系统内部仍需保存完整的 `core_question`，否则“风险约束”这类短标题无法精确约束后续报告生成和更新。

推荐结构：

```json
{
  "title": "存储需求",
  "core_question": "深度学习模型和算力架构变化会怎样影响内存容量、带宽及产品需求？",
  "leadership_value": "用于判断产品路线、客户机会和投入优先级",
  "scope_in": ["容量", "带宽", "内存层级", "应用需求"],
  "scope_out": ["与存储需求无关的通用模型原理"],
  "evidence_ids": ["E12", "E19"],
  "evidence_status": "limited"
}
```

## 3 生成流程

### 3.1 识别决策任务，而不是只做 Topic 分类

同一个 Topic 会因为提问方式不同而产生不同模块。系统应同时判断：

- 话题类型：新技术、市场变化、政策、竞争对象、经营问题。
- 用户意图：了解、评估影响、比较方案、决定投入、监测风险、制定行动。
- 公司对象：产品、客户、研发、制造、供应链、资本投入或组织能力。
- 时间尺度：近期处置、中期规划、长期跟踪。

例如 Topic 都是“深度学习”：

| 领导问题 | 合理的模块主线 |
| --- | --- |
| 技术会怎样演进 | 模型架构、训练范式、算力路线、演进信号 |
| 对长鑫有什么影响 | 存储需求、产品机会、客户变化、投入窗口、风险约束 |
| 是否在内部落地 | 落地场景、价值测算、数据基础、算力成本、风险治理 |
| 竞争对手做得怎样 | 技术路线、产品能力、客户进展、成本效率、生态布局 |

因此 Topic 类型只选择分析镜头，不能对应固定目录。

### 3.2 先生成检索计划

一次 Query 往往只能得到一种叙事。建议把 Web Search 查询拆成四组：

1. **核心事实查询**：Topic + 对象 + 指标 + 时间。
2. **影响链查询**：变化如何传导到产品、客户、成本、产能或风险。
3. **反向验证查询**：失败、限制、不适用、成本高、尚未量产、争议。
4. **一手来源查询**：监管披露、公司公告、标准、论文、测试、官方数据。

每个查询保存 `query_id`、检索目的、对应决策问题、生成时间和结果文献 ID。Query 只是检索意图，不能作为报告证据。

### 3.3 整理文献并生成证据议题卡

文献先按 `family_id`、正文指纹和来源 URL 去重，再逐篇评估：

- 与 Topic 的相关性。
- 对领导判断的价值。
- 是否为直接或一手材料。
- 对长鑫及具体业务场景的适用性。
- 时间是否仍有效。
- 角色是支持、反驳、限定还是背景。

随后从相关文献中提取“议题卡”，不要立刻命名模块：

```json
{
  "issue": "模型训练对内存带宽的需求上升",
  "management_implication": "可能影响产品组合和客户机会判断",
  "entities": ["训练集群", "DRAM"],
  "metrics": ["容量", "带宽"],
  "evidence_ids": ["E12", "E19"],
  "counter_evidence_ids": ["E25"],
  "applicability": ["训练场景"],
  "uncertainties": ["客户采购节奏尚不明确"]
}
```

### 3.4 先生成完整子问题，再压缩标题

根据议题卡和领导决策任务生成 8—12 个完整子问题，经过聚类和审查收敛到 4—6 个。筛选可使用以下工程评分：

```text
模块分 = 2×Topic相关性 + 3×决策价值 + 证据适用性 + 模块独立性
```

分数只用于排序候选，不能显示为置信度。硬性淘汰规则：相关性为 0、决策价值为 0、与其他模块完全重复。关键但缺资料的问题可以保留为 `gap`，通常不超过两个。

最后单独执行“名称压缩”：输入完整问题、边界及同级标题，输出 2—6 字标题。压缩时检查：

- 使用名词短语。
- 同组标题语法平行。
- 不包含报告、研究、分析等容器词。
- 不用文献标题或来源名称。
- 不因压缩丢失核心对象。
- 标题之间不能近义重复。

### 3.5 引入可维护的领导词汇偏好

仅靠 Prompt 很难长期稳定满足领导。建议记录领导对标题的“接受、改名、合并、删除、调序”，形成组织词汇偏好表：

```json
{
  "preferred_terms": ["产品路线", "投入窗口", "观察信号"],
  "avoid_terms": ["发展现状", "未来趋势", "综合挑战"],
  "aliases": {"商业应用": "落地场景"},
  "topic_type": "新技术或能力",
  "updated_by": "人工评审"
}
```

这个词表只影响命名和表达习惯，不能强制生成没有材料支持的模块。

## 4 Prompt 分工建议

建议拆成三个主要模型阶段，材料很多时再把证据提取分批：

1. `analyze_topic_and_search`：识别决策任务，生成多组 Query。
2. `build_module_candidates`：读取材料评估和议题卡，生成完整候选子问题。
3. `review_and_name_modules`：合并、淘汰、检查证据，压缩成 2—6 字标题。

第三阶段 Prompt 的关键约束：

```text
你输出的是给公司领导看的一级模块名称。
先根据完整核心问题判断模块是否影响选项、资源、风险、时点或观察信号；
再把通过审查的模块名称压缩为 2—6 个字符。
材料决定本次有哪些模块，组织视角只决定如何解释其管理意义和优先级。
不得为了覆盖预设维度增加没有证据的正式模块。
同级标题必须边界不同、颗粒度一致、语法平行。
禁止使用：背景、现状、趋势、挑战、展望、综合分析。
```

## 5 评估方式

不要只看模型输出是否“听起来不错”。准备脱敏真实样本，记录以下指标：

| 指标 | 计算方式 | 意义 |
| --- | --- | --- |
| 直接接受率 | 领导未改名的标题数 / 标题总数 | 名称是否符合使用习惯 |
| 结构接受率 | 未被删除或合并的模块数 / 模块总数 | 拆分是否有管理价值 |
| 证据覆盖率 | 有有效证据模块数 / 正式模块数 | 是否脱离材料 |
| 重复率 | 被评为同义模块的模块对 / 全部模块对 | 边界是否清楚 |
| 话题敏感度 | 同一 Topic 更换领导问题后结构发生合理变化 | 是否摆脱固定模板 |
| 检索贡献率 | 最终引用文献对应的 Query 数 / Query 总数 | Query 是否有效 |

推荐先选 20—30 个历史 Topic 做离线评审，每类 Topic 都覆盖。领导直接参与的样本可以少，但业务人员要用同一评分表代评，并保存最终人工标题作为回归基线。
