# 整体与子问题报告更新方案

## 1 更新的核心不是“重写”，而是“认知增量路由”

更新接口收到问题、回答和本轮 Web Search 信源后，不应直接把全部内容与旧报告拼在一起，让模型返回一篇新报告。更可靠的做法是：

1. 固定本轮被采纳的回答范围。
2. 从被采纳内容中提取可独立核实的认知增量。
3. 用本轮及历史材料验证每条增量。
4. 判断它应该更新哪个子问题报告。
5. 判断它是否达到总体报告的联动门槛。
6. 对目标内容块生成局部修改计划。
7. 输出完整候选报告，经过审查和用户确认后提交。

Web Search 的 Query 用于解释“为什么检索这些材料”和检查检索覆盖，但 Query 本身不是证据。检索结果与回答相关，也不等于能支持回答中的全部主张。

## 2 推荐的报告组织

如果总体报告和子问题报告是独立文件，建议形成一个报告包：

```text
reports/<topic_id>/
  overview.md                 # 领导主要阅读的总体报告
  subtopics/
    <module_id>.md            # 每个子问题的详细报告
  manifest.json               # 模块、文件、版本、依赖关系

history/<topic_id>/<batch_id>/
  before/
  after/
  changes.md
  evidence_decisions.json
```

`manifest.json` 至少保存：总体报告版本、各子报告版本、稳定 `module_id`、核心问题、文件路径，以及总体摘要依赖哪些子问题结论。标题可以改，ID 不随标题变化。

如果当前只有一个 Markdown 文件，也可先把一级标题视为子问题报告，用 `block_id + text_hash` 做定位。接口设计仍按相同逻辑运行，后续拆成多个文件时不必重写认知增量算法。

## 3 输入应明确分区

```json
{
  "topic_id": "deep-learning",
  "base_versions": {
    "overview": 8,
    "subtopics": {"m_storage": 5}
  },
  "turn": {
    "turn_id": "t102",
    "question": "大模型架构变化会提升内存需求吗？",
    "answer_revision": "a3",
    "answer_segments": [],
    "accepted_segment_ids": []
  },
  "search": {
    "queries": [],
    "documents": []
  },
  "previous_turn": {},
  "organization_context": {}
}
```

各输入职责：

| 输入 | 作用 | 不能作为 |
| --- | --- | --- |
| 本轮问题 | 解析对象、条件和用户真正关心的判断 | 事实证据 |
| 被采纳回答片段 | 确定本轮允许提出哪些更新 | 已验证事实 |
| Query 及检索目的 | 解释检索范围，发现材料覆盖缺口 | 报告引用 |
| 本轮信源 | 支持、反驳或限定本轮增量 | 与回答无关内容的自动写入许可 |
| 历史信源 | 核对旧结论依据，判断是否被新材料改变 | 旧结论永远正确的保证 |
| 上一轮问答 | 解析“这个方案”等指代 | 自动写入内容或事实证据 |
| 当前报告及版本 | 提供旧观点和修改基线 | 可以被整体重写的草稿 |

如果上游不能提供明确采纳状态，更新接口只能返回预览，不应自动提交。推荐保存 `accepted_segment_ids` 和 `answer_revision`，防止用户采纳 A 版回答，接口却读取 B 版。

## 4 更新算法

### 4.1 解析本轮范围

从问题、被采纳片段和必要的上一轮上下文中得到：讨论对象、时间、场景、假设、约束和未解析指代。未采纳内容不进入后续阶段。

### 4.2 整理本轮与历史材料

对文献去重并逐篇评估相关性、决策价值、直接性、公司适用性、时效性和证据角色。支持、反驳和限定材料都保留。材料排序只决定处理顺序，不决定旧观点是否被覆盖。

不同主张使用不同来源：公司内部经营事实优先内部原始记录；市场、竞争、政策和外部技术事实优先一手公开材料；预测必须保留作者、假设和预测语气。同一底稿的转载不重复加权。

### 4.3 提取候选认知增量

每条增量应是能独立判断的新命题，并记录：

```json
{
  "delta_id": "d_17",
  "proposition": "训练侧需求更强调内存带宽，但客户采购节奏仍不明确",
  "kind": "assessment",
  "applicability": ["训练场景", "当前时间范围"],
  "accepted_segment_ids": ["a3_s2"],
  "evidence_links": [],
  "counter_evidence_links": [],
  "support_status": "partial",
  "limitations": ["缺少客户采购数据"]
}
```

只允许被采纳回答产生更新意图。材料可以支持、限定或反驳这项意图，但不能因为某篇材料很重要就自动新增无关报告内容。

### 4.4 判断新旧关系

将增量与目标子问题中的旧观点比较，关系至少分为：

| 关系 | 处理 |
| --- | --- |
| `duplicate` | 不改正文，可记录重复核实 |
| `add` | 增加新的独立观点 |
| `strengthen` | 增加证据或提升表述强度，但不得超过证据支持 |
| `qualify` | 为旧判断增加对象、时间、场景或条件限制 |
| `correct` | 新证据直接推翻旧事实，保留旧版本并修正当前版本 |
| `conflict` | 无法消解时保留双方观点和待验证项 |

不能因为新文献发布时间更近或篇数更多就执行 `correct`。先比较对象、时间、统计口径、方法和适用场景。

### 4.5 先路由到最具体的子问题

每条增量先匹配最具体的 `module_id`，评分可考虑：核心问题语义、纳入排除范围、旧观点相似度和证据对象。只有匹配唯一且超过阈值时才自动定位；多个模块接近时返回澄清或人工选择。

子问题报告是详细事实、推导和证据的主要落点。总体报告只保留跨模块或影响领导决策的内容，避免每一轮对话都让总体报告变长。

### 4.6 总体报告联动门槛

增量满足下列任一条件，才建议联动总体报告：

- 改变 Topic 的总体结论或判断方向。
- 改变模块之间的优先级。
- 改变重大投入、资源配置或行动选项。
- 新增或解除重要风险。
- 改变行动窗口或复盘时点。
- 改变领导需要持续观察的关键指标。

例如：

| 新增认识 | 子问题报告 | 总体报告 |
| --- | --- | --- |
| 某篇论文补充了一种模型结构细节 | 更新“模型架构” | 通常不改 |
| 新证据显示内存需求变化会影响产品路线 | 更新“存储需求” | 更新影响摘要或优先级 |
| 两个来源对市场规模口径冲突 | 更新对应子问题并保留分歧 | 只有影响总体判断时增加风险提示 |
| 用户明确要求近期不投入 | 更新“投入窗口”为用户约束 | 若改变建议则联动总体建议 |

### 4.7 构建更新依赖图

更新不能只检查目标段落。建议维护：

```text
证据 → 子问题观点 → 子问题结论 → 总体摘要/建议
```

底层事实改变后，沿依赖图检查上层内容是否仍成立。检查不代表必须修改；仍成立则记录 `keep`，只有产生实质不一致才联动修改。

### 4.8 生成局部修改计划

模型只能对程序允许的块生成操作：修改正文块、向现有章节追加、在明确授权时新增或重命名章节。每个操作必须包含：

- 目标文件、块 ID 和旧文本哈希。
- 修改前后文本。
- 对应增量和被采纳片段。
- 证据引用和保留限制。
- 为什么修改这个位置。
- 对领导判断的影响。

删除、移动章节和全文重写不应作为普通模型操作开放。

### 4.9 审查与提交

提交前分两层检查：

1. 程序校验引用存在、引文逐字匹配、数字单位有来源、目标块属于允许范围、旧哈希未变化、每个增量都有处理结果。
2. 独立语义审查证据是否蕴含新表述、是否扩大范围、是否漏掉反证、总体报告与子问题是否一致。

普通的证据补充和局部限定可按公司策略自动提交。总体结论、建议、资源优先级、风险等级、模块结构发生变化时，必须返回完整候选总体报告和相关子问题报告供用户确认。

## 5 多报告版本的一致提交

如果一次更新同时影响总体报告和一个或多个子问题报告，应生成一个 `update_batch`：

```json
{
  "batch_id": "ub_20260915_001",
  "base_versions": {"overview": 8, "m_storage": 5},
  "candidate_versions": {"overview": 9, "m_storage": 6},
  "changes": [],
  "confirmation_required": true
}
```

确认后再次检查所有基线版本。任何一个文件已变化，就拒绝整批提交并重新生成预览；不能只提交一半。写入时先产生临时文件，再原子替换清单和最新版本指针。所有更新前、更新后文件及 `changes.md` 永久保存。

## 6 用户怎样判断“为什么该改”

领导主要看完整报告，因此候选报告应直接呈现修改后的整体内容。研发和报告负责人同时获得逐项审计记录：

```text
修改位置：总体报告 / 管理摘要
修改原因：子问题“存储需求”的结论由“可能增加”变为“训练侧更明确、推理侧仍待验证”
支持证据：E12/P3、E19/P7
限定/反证：E25/P2
修改前：……
修改后：……
领导影响：产品机会判断需要区分训练与推理场景
审查结论：合理；尚缺客户采购节奏数据
```

这使“改了什么”和“为什么合理”都可以追溯，同时避免让领导只阅读技术性的 Diff。

## 7 关键失败策略

- 没有被采纳片段：只返回建议，不进入提交。
- 指代不清：返回 `needs_clarification`。
- 证据不足或回答夸大：返回 `evidence_insufficient`，保留旧报告。
- 新旧来源冲突无法消解：记录 `conflict`，不投票覆盖。
- 子问题定位不唯一：返回候选模块让用户选择。
- 总体与子报告基线版本过期：返回 `version_conflict`。
- 最终审查不通过：不创建新版本。
