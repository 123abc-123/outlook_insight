# 接口与实施路线

## 1 不必增加新的业务接口

外部仍可保持两个接口：

- `POST /decompose`：生成模块短标题、完整子问题和证据映射。
- `POST /update`：`prepare` 生成跨总体与子问题报告的候选更新，`commit` 提交用户确认的原候选版本。

优化主要体现在接口字段和内部函数，不需要让调用方理解全部模型阶段。

## 2 拆分接口建议字段

输入新增或明确：

```json
{
  "topic": "深度学习",
  "leadership_question": null,
  "organization_context": {},
  "research_scope": {},
  "search_queries": [],
  "documents": []
}
```

输出保留短标题和详细契约：

```json
{
  "topic_type": "新技术或能力",
  "decision_task": "评估影响与投入",
  "themes": ["模型架构", "落地场景", "存储需求", "投入窗口", "风险约束"],
  "modules": [],
  "rejected_candidates": [],
  "search_gaps": [],
  "structure_version": "..."
}
```

生产环境可不向普通前端返回 `rejected_candidates`，但建议在调试或评审记录中保存候选、淘汰原因和标题压缩前的完整问题。

## 3 更新接口建议字段

`prepare` 输入：

```json
{
  "action": "prepare",
  "request_id": "...",
  "topic_id": "...",
  "base_versions": {},
  "adoption": {
    "turn_id": "...",
    "answer_revision": "...",
    "accepted_segment_ids": []
  },
  "current_turn": {
    "question": "...",
    "answer_segments": []
  },
  "search_context": {
    "queries": [],
    "documents": []
  },
  "previous_turn": {},
  "historical_documents": [],
  "confirmation_policy": "auto_routine"
}
```

`prepare` 输出：

```json
{
  "status": "preview_ready",
  "batch_id": "...",
  "base_versions": {},
  "candidate_versions": {},
  "candidate_overview": "完整 Markdown",
  "candidate_subreports": {},
  "changes": [],
  "evidence_decisions": [],
  "unresolved_items": [],
  "confirmation_required": true
}
```

`commit` 只提交 `batch_id/preview_id` 对应的候选原文，不再次调用模型，避免用户看到的内容和最终落盘内容不一致。

## 4 内部函数拆分

```python
def analyze_topic_and_generate_queries(topic_context): ...

def rank_and_extract_evidence(documents, decision_context): ...

def generate_module_contracts(topic_context, evidence): ...

def prepare_update_bundle(turn_context, report_package): ...

def commit_update_bundle(preview_id, expected_versions): ...
```

`prepare_update_bundle` 内部再细分：

```text
resolve_scope
  → rank_documents
  → extract_change_candidates
  → compare_evidence_with_existing_claims
  → match_subtopics
  → compare_old_and_new
  → decide_overview_propagation
  → plan_local_operations
  → review_dependencies
  → review_update_bundle
```

每个阶段使用结构化 JSON Schema，程序校验 ID、引用、版本和操作范围。Prompt 负责语义判断，确定性约束放在代码中。

## 5 推荐分阶段落地

### P0 先补齐可追溯输入

- 保存 Query、检索目的、检索时间和文献 ID 对应关系。
- 固定回答修订号及被采纳片段 ID。
- 为总体报告、子问题报告和 Markdown 块建立稳定 ID 与版本。
- 保存文献 `family_id`、来源类型、时间、发布机构和适用对象。

缺少这些字段时，Prompt 再好也很难稳定判断应该改哪里、依据来自哪里。

### P1 优化关键词生成

- 增加决策任务识别。
- 将完整子问题生成与 2—6 字命名分开。
- 增加候选合并、边界审查和 `gap` 控制。
- 建立领导词汇偏好表和脱敏回归样本。

### P2 优化单个子问题更新

- 落实采纳范围、回答与证据双触发、认知变更判定和局部 Markdown 操作。
- 先稳定更新一个目标子问题。
- 建立引用、数字、范围、版本和语义审查。

### P3 支持总体报告联动

- 增加子问题到总体摘要/建议的依赖关系。
- 加入总体报告联动门槛。
- 实现跨文件 `update_batch`、完整预览与一致提交。

### P4 用真实样本校准

- 统计领导标题改名、合并、删除和调序行为。
- 统计修改块准确率、无依据修改率、错误联动率。
- 根据真实错误调整 Prompt、词汇偏好和阈值，不把模型自评分当成最终效果。

## 6 第一轮验收标准

| 能力 | 验收要求 |
| --- | --- |
| 模块命名 | 每个 2—6 字；无泛化标题；同级颗粒度一致 |
| 话题适配 | 同一 Topic 更换领导问题后，模块主线发生合理变化 |
| 证据绑定 | 正式模块均有有效材料或明确标为关键 `gap` |
| 更新范围 | 未采纳内容和无关文献不进入报告修改 |
| 子问题路由 | 每条候选变更定位到唯一目标，歧义时不自动修改 |
| 总体联动 | 只有达到管理影响门槛的认知变更改变总体报告 |
| 可解释性 | 每处修改都有位置理由、证据、限制和领导影响 |
| 版本安全 | 过期基线拒绝提交；总体与子报告不会只成功一部分 |
| 用户确认 | 核心结论、建议、优先级、风险和结构变化均提供完整候选报告确认 |

## 7 建议优先实现的最小闭环

第一轮先实现下面四项，收益最大：

1. 完整子问题与 2—6 字标题分两步生成。
2. 保存 Query 与文献的关联，并主动检索反向材料。
3. 更新时先匹配子问题，设置总体报告联动门槛。
4. 用一个预览批次同时展示总体和子问题候选报告，确认后一次提交。

这四项能直接改善领导看到的目录质量，同时显著减少更新接口乱改全文的风险。
