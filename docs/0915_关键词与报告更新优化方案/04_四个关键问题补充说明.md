# 四个关键问题补充说明

## 1 更新不是默认增加内容

这里更准确的名称应是“认知变更判定”，不是“认知增量更新”。一次处理可能产生六种结果：

| 新材料与当前报告的关系 | 当前版本操作 | 是否需要确认 |
| --- | --- | --- |
| 新增了有效认识 | `add`：加入目标子问题 | 重要结论或建议需要 |
| 补强旧观点 | `add_evidence` 或 `strengthen` | 表述强度变化时需要 |
| 限定旧观点 | `qualify`：缩小对象、时间或场景 | 影响结论时需要 |
| 直接推翻旧观点 | `revise` 或 `retire`：修正或退出当前版本 | 必须确认 |
| 新旧证据暂时无法消解 | `mark_disputed`：保留分歧和待验证项 | 必须确认 |
| 没有实质变化或与报告无关 | `no_change` | 不需要 |

需要支持两条变更触发链：

1. **回答触发**：从最终回答或被采纳片段中提取候选主张，再用信源核实。
2. **证据触发**：在本轮问题范围内，信源直接反驳当前报告中的相关旧观点，即使回答没有完整说出该冲突，也要提出修正、退出或争议标记。

“删减相悖内容”不能由模型直接删除一段字符串。建议增加受控操作 `retire_claim`：必须指向稳定的观点或 Markdown 块 ID，提供原文哈希、相悖证据、对象时间口径对比和退出原因。旧内容从当前有效报告中移除，但仍完整保存在历史版本和变更记录中。

只有满足以下条件才能执行 `retire`：

- 新材料直接涉及旧观点，而不是外围相关。
- 新旧材料讨论的对象、时间、场景和统计口径可比。
- 新材料足以否定旧表述，而不只是提出另一种可能。
- 旧观点无法通过增加限定条件继续成立。
- 删除后检查摘要、建议和其他依赖内容。
- 用户确认完整候选报告。

如果新旧来源都有效但结论不同，应 `mark_disputed`，不能按文献篇数删除其中一方。如果新材料只是没有提到旧观点，应 `no_change`，不能把“本轮没搜到”当成“旧观点错误”。

推荐中间结构：

```json
{
  "change_id": "chg_17",
  "trigger": "answer|evidence",
  "target_claim_id": "claim_storage_03",
  "relation": "new|supports|qualifies|contradicts|conflicts|unrelated",
  "action": "add|add_evidence|revise|retire|mark_disputed|no_change",
  "before": "旧观点",
  "after": "候选新表述",
  "evidence_links": [],
  "comparison": {
    "subject": "same",
    "time": "same",
    "scenario": "same",
    "metric_definition": "same"
  },
  "reason": "为什么应该采取该操作",
  "management_impact": []
}
```

## 2 只有一个 Topic 时如何自适应拆分

当前接口没有单独的领导问题，因此不能把“解析领导问题”作为必需步骤。系统只能解析 Topic 原文本身是否包含明确对象或目的；原文没有时，采用综合认知模式。

### 2.1 解析四类变量

```json
{
  "topic": "深度学习",
  "analysis_mode": "overview|focused",
  "explicit_intent": null,
  "intent_source": "default_overview|query_explicit",
  "decision_object": ["产品路线", "内部应用", "竞争应对"],
  "decision_variables": ["需求", "成本", "风险", "时点"],
  "time_horizon": "近期|中期|长期"
}
```

Topic 原文决定是否存在显式意图；公司领导关注配置用于补充管理视角；检索材料用于确认哪些议题真实存在。三者的关系是：

```text
Topic 明示目的时决定“聚焦什么”；未明示时使用“综合认知”
公司上下文决定“判断对谁有用”
信源材料决定“本轮有什么可讨论”
```

### 2.2 动态生成候选问题

先从信源提取议题卡，再把议题卡映射到 Topic 类型和长鑫相关性。候选模块不是从固定模板选择，而是由下面的交集产生：

```text
候选模块 = 材料议题 ∩ Topic 边界 ∩ Topic类型维度 ∩ 公司适用范围
```

随后计算候选模块的相关性、决策价值、证据适用性和独立性，合并重复项，收敛为 4—6 个完整子问题，最后才压缩为 2—6 字标题。

### 2.3 同 Topic 的实际例子

以下差异只有在 Topic/Query 原文明确写出时才成立：

| Topic/Query | 分析模式 | 可能的主题 |
| --- | --- | --- |
| 深度学习技术路线接下来怎么变 | 聚焦：技术演进 | 模型架构、训练范式、算力路线、演进信号 |
| 深度学习对长鑫的产品机会是什么 | 聚焦：外部影响 | 存储需求、产品机会、客户变化、投入窗口、风险约束 |
| 公司内部是否应该应用深度学习 | 聚焦：内部落地 | 落地场景、价值测算、数据基础、算力成本、风险治理 |
| 竞争对手的深度学习布局到什么程度 | 聚焦：竞争应对 | 技术路线、产品能力、客户进展、生态布局、竞争影响 |

如果输入只有“深度学习”，系统应直接使用综合认知模式，根据材料形成“模型架构、落地场景、算力需求、存储影响、产业格局、风险信号”等候选，再按实际证据删减或合并。不能随机选择上表中的某一种聚焦模式。

### 2.4 代码实现建议

```python
profile = profile_topic(topic, organization_context)
issues = extract_evidence_issues(ranked_documents)
candidates = build_candidates(topic, profile, issues)
selected = review_and_select(candidates, target_count=(4, 6))
modules = compress_titles(selected, min_chars=2, max_chars=6)
```

`profile_topic` 只能提取 Topic 原文明示的信息；若没有具体目的，则输出 `analysis_mode=overview`。`review_and_select` 必须输出每个候选保留、合并或淘汰的理由，以便用真实领导反馈校准。

## 3 子问题更新后如何决定是否联动总体报告

这一能力需要“依赖关系 + 规则门槛 + 语义审查”，不能只让模型自行判断。

### 3.1 先保存依赖关系

总体报告中的摘要和建议要记录其来源模块：

```json
{
  "overview_block_id": "summary_02",
  "depends_on_module_ids": ["m_storage", "m_customer"],
  "depends_on_claim_ids": ["claim_storage_03", "claim_customer_01"]
}
```

每个子问题报告同时输出一份结构化 `module_summary`：当前结论、优先级、建议、风险等级、行动时点和观察信号。这样代码可以比较子问题更新前后的管理含义。

### 3.2 代码执行联动门槛

第一版建议使用可解释的硬规则。子问题发生以下变化时设置 `propagate_to_overview=true`：

- 结论方向改变，例如“值得投入”变为“暂缓投入”。
- 总体建议或行动选项需要改变。
- 模块优先级发生实质变化。
- 新增、解除或提高重大风险。
- 决策窗口、最晚行动时间或复盘节点改变。
- 总体报告跟踪的关键观察信号改变。

只增加技术细节、案例、引用或不改变结论的限定时，通常只更新子问题报告。

```python
impact = compare_module_summary(before_summary, after_summary)
propagate = any([
    impact.conclusion_changed,
    impact.recommendation_changed,
    impact.priority_changed,
    impact.material_risk_changed,
    impact.decision_timing_changed,
    impact.key_signal_changed,
])
```

这里先由程序根据结构化字段触发，再把更新前后的子问题结论、依赖的总体块和证据交给模型生成候选总体表述。模型不能自由修改无依赖关系的其他摘要。

### 3.3 完整执行流程

```text
更新子问题中的目标观点
    ↓
重新生成该子问题的 module_summary
    ↓
程序比较前后管理字段
    ↓
未过门槛：总体报告 no_change
通过门槛：召回依赖该模块的总体块
    ↓
模型提出局部总体修改
    ↓
独立审查总体与子问题是否一致
    ↓
返回总体报告 + 子问题报告的完整候选版本
    ↓
用户确认后作为同一批次提交
```

如果现阶段没有依赖关系，可以临时用模块 ID、标题路径和语义召回寻找总体块，但所有总体报告修改都应要求确认。依赖关系建立后再考虑自动化普通联动。

## 4 Query 到底参不参与更新

Query 参与更新流程，但不作为事实证据。它有四个用途：

1. **解析检索意图**：说明这一轮想验证哪个对象、指标、时间或假设。
2. **判断材料相关性**：帮助排序 Query 返回的信源是否回答了检索目的。
3. **检查覆盖缺口**：判断是否只查了支持方向，没有查反证、限制或一手来源。
4. **审计检索过程**：记录某篇文献由哪个 Query 找到，方便复现。

Query 不能承担证据作用，因为它通常是问题、关键词或待验证假设。例如：

```text
Query：深度学习将使 DRAM 需求翻倍
```

这句话可能只是搜索词，不能因此把“DRAM 需求将翻倍”写入报告。只有返回文献中的具体数据、方法、对象和原文片段能够支持该主张时，文献才是证据。

推荐的数据链是：

```text
用户问题
  → query_id + query_text + search_purpose
  → document_id + metadata
  → segment_id + 原文
  → evidence_ref
  → change_decision
  → report operation
```

因此 Query 会传给范围解析和材料整理阶段，也会写入审计记录；最终修改的 `evidence_refs` 只能引用文献片段，不能引用 `query_text`。

## 5 与当前仓库代码的差距

以上内容是目标实现。当前仓库已经具备部分基础，但还没有完整支持这四项：

| 能力 | 当前代码 | 需要增加 |
| --- | --- | --- |
| 删除相悖旧观点 | `plan_update` 明确禁止删除；只能修改或追加 | `retire_claim` Schema、反证和范围校验、依赖检查、强制预览确认 |
| 自适应拆分 | `leadership_question`、公司上下文和 Topic 视角直接进入候选模块 Prompt | 独立 `DecisionContext` 解析、候选保留/淘汰原因、完整问题与短标题分步生成 |
| 总体报告联动 | 同一 Markdown 内会检查部分摘要和建议 | 总体与子报告清单、`module_summary`、显式依赖、联动门槛和跨文件提交批次 |
| Query 参与更新 | `/update` 当前只接收文献，没有 Query 结构 | `search_context.queries`、Query—文献映射、覆盖检查和审计记录 |

因此，如果按照本补充方案继续开发，需要修改接口 Schema、Prompt、更新操作类型、版本存储和测试，不能只调整一段 Prompt。
