# 认知雷达话题拆分实现方案

版本：讨论稿 v1.0

适用环节：用户输入 Topic 后，利用已有内外部检索结果形成初始报告的模块结构

读者：产品与研发人员

## 1 设计结论

建议采用“管理问题引导候选模块，文献决定具体内容，质量检查确定最终结构”的实现方式。

直接让模型根据文献生成目录，容易得到“背景、现状、挑战、展望”等通用模块；只做文献聚类，又容易让材料最多的技术细节占据报告主体。认知雷达服务领导，模块应当帮助领导理解变化、判断影响和比较选择，因此需要把“文献在讨论什么”进一步转换成“这个问题会影响领导的什么判断”。

最终模块是一组值得持续追踪的管理问题。每个模块必须有明确边界、与 Topic 的关联、对判断的用途及证据映射。模块名称可以是“业务价值与优先场景”，其内核应是“哪些场景值得优先验证，以及排序依据是什么”。

本方案不实现 WebSearch、文献元信息采集或完整报告生成。默认上游已经提供文献 ID、正文或片段、来源类型及元信息；本功能复用这些数据。如果需要补充检索，只输出检索请求，由已有检索服务执行。

## 2 接口输入与输出

### 2.1 输入

```ts
type DecomposeRequest = {
  topic: string;
  documents: DocumentRef[];           // 复用已有文献结构
  research_scope?: {
    time_range?: string;
    geography?: string;
    business_scope?: string;
  };
  organization_context?: {
    industry?: string;
    business_priorities?: string[];
    known_constraints?: string[];
  };
  leadership_question?: string;      // 如“是否值得在明年扩大投入”
};
```

`topic + documents` 是最低可用输入。组织背景和领导关注问题有则使用，没有也能运行，但输出必须声明采用的研究范围与假设，不能把模型猜测写成“我司现状”。例如，“AI Agent”本身不足以推出用户所在行业；系统可以先给出企业应用视角，并将行业适用性标为待补充。

### 2.2 输出

```ts
type Module = {
  module_id: string;                 // 服务端生成，后续更新保持稳定
  title: string;
  core_question: string;
  leadership_value: string;          // 该模块能支持什么判断
  scope_in: string[];
  scope_out: string[];
  sub_questions: string[];
  evidence_refs: EvidenceRef[];      // 文献 ID 与片段定位
  evidence_status: "supported" | "limited" | "gap";
  missing_information: string[];
  priority_reason: string;
};

type DecomposeResult = {
  status: "ready" | "provisional" | "insufficient_input";
  topic_interpretation: string;
  assumptions: string[];
  themes: string[];                 // 供前端直接展示的精炼主题名
  modules: Module[];
  pending_questions: string[];
  supplemental_search_requests: SearchRequest[];
  structure_version: string;
};
```

`EvidenceRef` 和 `SearchRequest` 使用现有系统定义，不另建文献元信息体系。`supported` 表示有材料支持讨论该模块的问题，不表示模块下所有判断都已证实。无有效材料时，可返回有明确标识的暂定结构；不能返回“已由文献验证”的正式结构。

## 3 如何产生对领导有价值的拆分

### 3.1 先识别本次话题的主要判断任务

建立一个小型“分析视角库”，它用于生成问题，不是固定报告模板。每次选择一个主视角，必要时补充一个辅助视角，避免把所有视角平铺成十几个模块。

| 话题类型 | 领导通常需要理解或判断什么 | 可采用的拆分视角 |
| --- | --- | --- |
| 新技术或新能力 | 值得关注到什么程度，适用于哪些业务，何时试点 | 业务价值、成熟度、投入条件、实施风险、验证路径 |
| 行业或市场变化 | 变化是否持续，影响哪些业务，有什么应对选择 | 变化及驱动、影响传导、格局变化、机会与暴露、观察信号 |
| 政策或监管变化 | 适用范围是什么，影响哪些业务，需要何时响应 | 适用边界、业务影响、能力缺口、响应安排、未明确事项 |
| 竞争对手或标杆企业 | 对方发生了什么变化，对我方意味着什么 | 战略意图、能力与动作、效果证据、竞争影响、可借鉴条件 |
| 经营管理问题 | 问题在哪里，为什么发生，有哪些可选措施 | 问题规模、原因及证据、可选措施、成本与约束、验证指标 |

这些问题是分析提示，不预设答案。用户只是希望了解趋势时，可以形成“变化、影响、分歧、观察信号”的认知结构，不必强行要求每个模块都给出投资或执行建议。对于混合话题，根据用户关注的问题确定主线；无法判定时记录默认视角。

长鑫场景在 `config/radar.toml` 中配置默认组织背景和分 Topic 关注重点。新技术话题重点检查技术成熟度、量产窗口、良率质量成本和客户验证；市场话题重点检查需求、价格库存、竞争产能及其经营传导；政策话题重点检查适用边界、供应链与技术获取、响应时点；竞争对象话题重点检查对方实际能力、产品产能客户动作以及对长鑫的影响；经营问题则围绕问题规模、根因、经营权衡、资源和验证指标组织。每次选择其中一个主视角，不能把这些维度全部平铺成固定目录。

### 3.2 先整理材料，再提取证据单元

去重后先执行 `rank_documents`。模型必须逐篇判断相关性、决策价值、直接性、公司适用性、时效性和证据角色，程序再按 `4×相关性 + 3×决策价值 + 2×适用性 + 直接性 + 时效性` 排序。这个分数只决定处理顺序，不代表事实置信度。支持、反驳和限定主张的相关材料全部保留；只有与 Topic 和领导问题确实无关的材料才能剔除。同一 `family_id` 的转载先归并，不能靠篇数抬高权重。

排序后的相关材料再进入证据提取。这样既能让有限上下文优先处理有决策价值的材料，也能避免只选择支持当前结论的来源。

按文献或自然章节提取证据单元，不要先把全部文献压缩成一篇长摘要再拆分。每个单元保留：讨论的问题、事实或观点、适用对象、时间范围、重要限定条件，以及原始片段引用。

处理原则如下：

- 先做正文去重与转载归并。同一底稿的多篇转载属于同一个证据家族，不能因为数量多就提升模块优先级。
- 一份文献可以支持多个管理问题，不必被强制归入唯一分类。
- 区分已观察事实、作者判断和预测，不把预测转成已发生的事实。
- 有完整正文时优先使用正文；只有搜索摘要时标注支持范围，不能补出摘要未包含的结论。
- 内源主要帮助识别本公司的条件和影响，外源主要帮助理解外部变化；两者都按内容、时间和适用性判断，不设“内源永远更可信”的规则。

建议的中间结构：

```ts
type EvidenceUnit = {
  evidence_id: string;
  proposition: string;
  proposition_type: "observation" | "interpretation" | "forecast";
  subject: string;
  applicability: string[];
  qualifiers: string[];
  source_ref: EvidenceRef;
  evidence_family_id: string;
};
```

证据提取模型只处理来源内容；文献中出现的指令性文字属于引用材料，不改变系统处理规则。

### 3.3 从两个方向产生候选模块

第一路从证据出发，归纳文献反复讨论的问题，并提炼为管理问题。比如多份文献讨论推理时延、失败重试和人工复核，可以合并到“规模应用的成本与交付条件”，是否再拆开取决于 Topic 和管理用途。

第二路从管理问题出发，检查重要问题是否被材料遗漏。比如文献集中讨论技术能力，但领导的问题是“是否扩大投入”，那么投入条件和效果验证仍然值得检查，不能因为材料缺失就从结构中消失。

合并两路候选后，形成“候选模块 × 证据单元”的映射。区分三种情况：有直接材料支持、只有间接或局部材料支持、缺少材料。最后一种只能作为待验证问题或证据缺口，不能生成确定性结论。

建议先产生约 8—12 个候选，再收敛到约 4—6 个一级模块。这是初始可读性配置，不是强制凑数；窄话题可以只有 3 个模块，复杂话题可通过二级问题展开。

### 3.4 筛选时同时检查管理价值与证据基础

先执行三条硬检查：与 Topic 直接相关；能够说明其支持的管理判断；与其他模块存在可解释的边界。过不了检查的候选，删除或并入其他模块。

再对通过检查的候选进行排序。第一版可采用以下 0—2 分的人工可解释评分，每项附一句理由：

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 话题相关性 R | 间接或跑题 | 相关但外围 | 直接对应核心问题 |
| 判断价值 D | 无法说明用途 | 有助于理解背景 | 可能改变影响判断或选项排序 |
| 证据适用性 E | 无有效支持 | 局部或间接支持 | 有适用的直接证据 |
| 模块独立性 U | 与他项重复 | 存在交叉但可分 | 有明确独立问题 |

建议初始排序分为 `2R + 3D + E + U`。这是需要用样本调整的工程启发式，不能向用户显示成“置信度”。硬检查中相关性或判断价值为 0 的候选不进入正式模块；独立性为 0 时先合并。

重要且缺少证据的候选不因低分直接消失，而是进入缺口清单，必要时保留为 `gap` 模块。例如它决定了是否值得投入，却暂时没有公司内部成本数据，就应明确列出待补充的成本问题。

### 3.5 将模块名称写成具体管理议题

接口顶层 `themes` 只返回最终模块的精炼名称，`modules` 才携带核心问题、证据和缺口。标题必须是 2—6 个字符的管理主题，例如“模型架构、落地场景、存储需求”；Schema 同样设置 6 字符硬上限。不得使用文献标题、来源名称或文献得分。候选评分只用于筛选模块，系统没有“返回最高分文献”的逻辑。

| 容易出现的目录 | 更有价值的表达 | 改善原因 |
| --- | --- | --- |
| 技术介绍 | 技术成熟度 | 支持判断能否用于具体业务 |
| 应用案例 | 落地场景 | 支持场景排序，检查案例能否迁移 |
| 面临挑战 | 应用约束 | 明确制约实施的条件 |
| 未来趋势 | 观察信号 | 说明出现什么信号时应重新判断 |

名称仍应由实际内容决定。“技术原理”在某些话题中确有必要，但通常作为解释关键判断的二级问题，不默认占据一级模块。

## 4 推荐执行流程

```text
校验输入并明确 Topic 范围
    ↓
文献去重、逐篇评估与排序
    ↓
相关材料的证据单元提取
    ↓
选择主分析视角
    ↓
生成候选模块并绑定证据
    ↓
相关性检查  合并重复  评估判断价值
    ↓
检查重要缺口并按需请求补充检索
    ↓
形成稳定模块 ID 和模块契约
```

建议以四类独立的模型调用职责实现：

1. **材料整理**：逐篇输出结构化评估，程序验证文献 ID 完整性并排序，剔除确实无关的材料。
2. **证据提取**：可按相关文献分批执行，输出 `EvidenceUnit[]`。对文档内容版本计算缓存键，避免重复提取。
3. **候选生成**：读取 Topic 解释、管理视角和证据单元，输出候选模块及映射。保留证据片段以便核对，不只传摘要。
4. **结构审查与定稿**：检查边界、价值、覆盖和证据引用，输出最终结构与缺口。格式、引用存在性、ID 唯一性等由程序校验。

当材料很少时，可合并前两个调用以降低开销，但保留中间结构。模型输出不合规时进行一次带错误信息的修复；仍失败则返回结构化失败，不使用无法解释的目录兜底。

补充检索应有次数和结果量上限。第一版建议最多一轮，分别针对缺口、相反观点或内部约束生成查询；在内网环境无法即时获得材料时直接输出待补充项，不能等待外网请求无限挂起。

## 5 模型任务约束示例

候选生成调用可采用以下任务说明，具体字段由结构化输出约束：

```text
目标：围绕用户 Topic 形成供公司领导理解和判断的报告模块。

输入分区：
A 用户话题与明确提供的组织背景
B 本次研究范围和选定分析视角
C 有 ID 的证据单元及原文片段

要求：
1 每个候选模块回答一个相对独立的管理问题。
2 说明该问题为什么影响本话题的判断，避免套用通用目录。
3 只引用输入中的证据 ID，保留材料的适用边界。
4 缺少组织信息时，写待验证问题，不推断我司现状。
5 对重要但缺少证据的问题显式标记 gap。
6 提供纳入范围和排除范围，供后续报告更新定位。
7 不生成完整报告，不给出证据未支持的公司级行动结论。
```

审查调用要返回具体问题与处理结果，例如“两个模块都在回答优先应用场景，已合并”，不能只返回“质量良好”。

## 6 贯穿示例

以下全部为虚构输入，用于解释算法，不代表真实行业研究结果。

Topic 为“AI Agent 在企业客服中的应用”。用户希望理解是否值得试点；材料包括外部案例 E1、外部失败分析 E2、内部流程说明 I1、内部成本材料 I2。案例只涉及常见咨询，内部材料表明复杂问题需要人工复核。

建议模块如下：

| 模块 | 核心问题 | 判断用途 | 支持与缺口 |
| --- | --- | --- | --- |
| 优先场景 | 哪类咨询值得先验证 | 确定试点范围和价值假设 | E1、I1；缺少本公司实际效果 |
| 能力边界 | 能完成什么，何时必须转人工 | 确定可接受的服务边界 | E1、E2、I1 |
| 成本结构 | 系统、知识和人工投入是多少 | 判断试点是否可承担 | I1、I2；缺少规模化运行成本 |
| 风险责任 | 失误如何发现和处置 | 判断哪些场景可开放 | E2、I1 |
| 验证条件 | 用什么结果决定继续或调整 | 支持阶段性推进判断 | 由前述证据形成建议，验证标准待业务确定 |

“验证条件”中的建议是基于证据的分析产物，必须标注推导依据及待确定事项。不能伪装成文献已经证明的事实。

同样的外部材料，如果 Topic 改为“AI Agent 将如何改变客服行业竞争”，主线就应改为价值分配、成本与服务模式、竞争格局、组织影响和观察信号。模块不是关键词到固定目录的一对一映射。

## 7 与后续报告生成及更新的接口

模块输出应成为报告的“组织契约”：一级模块 ID 稳定；核心问题和边界可供生成报告时约束内容，也可供更新时定位观点。模块顺序由研究主线决定，不在每轮更新时重新按分数排序。

初次报告生成器在每个模块下写入独立观点，并保存观点 ID、支持证据和适用条件。展示模板可以之后调整，模块 ID 与观点 ID 不依赖标题文本、段落序号或 Markdown 行号。

新增事实通常进入现有模块。后续出现无法容纳的新管理问题时，才提出模块新增或边界调整，具体规则见《认知雷达报告更新实现方案》。

## 8 验收与第一版范围

准备至少覆盖新技术、行业变化、政策变化、竞争对象、经营问题的样本集，并加入宽泛 Topic、重复转载、全是外源和证据不足的情况。数量按可用样本确定，指标阈值在评审后设定，不能把本方案建议当成已验证效果。

| 检查项 | 可验证的结果 |
| --- | --- |
| 管理价值 | 评审者能解释每个模块支持的判断；统计不能解释的模块占比 |
| 话题适配 | 同一批材料换不同关注问题后，模块主线随之变化 |
| 非重复性 | 不存在两个模块核心问题相同、仅名称不同的情况 |
| 引用有效性 | 输出证据 ID 全部存在，抽检原文确实支持所讨论的问题 |
| 组织事实边界 | 未输入组织现状时，不出现未经支持的“我司已经”陈述 |
| 缺口诚实性 | 关键问题无证据时保留缺口，不生成虚构结论 |
| 数量鲁棒性 | 加入同源转载不会显著提高该问题的优先级 |

第一版实现主分析视角选择、证据提取、候选生成、结构审查及模块契约即可。先由人工评审校准模块价值，再考虑训练更复杂的排序模型；无需把模型自评分当成质量事实。
